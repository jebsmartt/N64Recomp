# Mario Golf 64 Recompilation Pipeline

This document covers the Mario Golf-specific usage of this N64Recomp fork. It is maintained on the `mariogolf` branch and is not intended to be merged upstream.

## Overview

This pipeline takes the ELF file produced by the [mariogolf64](https://github.com/jebsmartt/mariogolf64) decompilation project and produces recompiled C code for use by [MarioGolf64Recomp](https://github.com/jebsmartt/MarioGolf64Recomp).

The dependency chain is strictly one-directional:

```
mariogolf64 (decomp) → N64Recomp (this repo, mariogolf branch) → MarioGolf64Recomp (port)
```

## Prerequisites

- Python 3 with `pyelftools`: `pip install pyelftools --break-system-packages`
- A built `mariogolf64.elf` from the mariogolf64 repo (`make extract && make`)
- N64Recomp built from source (see main README)

## Files

| File | Purpose |
|---|---|
| `patch_elf.py` | Patches `mariogolf64.elf` to fix symbol metadata issues before recompilation |
| `mariogolf.toml` | N64Recomp configuration — entrypoint, output path, stubs |
| `mariogolf64_patched.elf` | Generated by `patch_elf.py` — gitignored |
| `recomp_output/` | Generated C files from N64Recomp — gitignored |

## Rebuild Pipeline

Run these commands after any change to the mariogolf64 decomp that affects the ELF:

```bash
# Step 1: Build the ELF from the decomp repo
cd ~/repos/mariogolf_recomp/mariogolf64 && make

# Step 2: Patch the ELF and generate recomp output
cd ~/repos/mariogolf_recomp/N64Recomp
python3 patch_elf.py
cd build && ./N64Recomp ../mariogolf.toml
```

A successful run prints `Function count: 4677` with no errors.

## ELF Patches (patch_elf.py)

The source ELF produced by mariogolf64 has several symbol metadata issues that prevent N64Recomp from correctly identifying and recompiling functions. `patch_elf.py` fixes these before running the recompiler.

### Patch 1: entry_TEXT_START NOTYPE → FUNC

**Problem:** The `.entry` section's start symbol `entry_TEXT_START` is typed `NOTYPE` because it is defined by the linker script rather than via a `glabel` directive. N64Recomp's entrypoint detection requires `STT_FUNC` type.

**Fix:** Set the `st_info` type byte of `entry_TEXT_START` to `STT_FUNC` (0x01) directly in the ELF symbol table.

**Note:** The entrypoint check in `elf.cpp` has a known signedness bug (`// TODO this never fires, the check is broken due to signedness`) that prevents the vram-based path from working regardless. The TOML does not set `entrypoint` for this reason — `has_entrypoint = false` bypasses the check entirely. This patch is retained for correctness but does not affect current behavior.

### Patch 2: ABS FUNC symbols → correct section

**Problem:** All libultra and NuSystem functions (`osSetIntMask`, `osInvalICache`, `bcopy`, etc.) are linked as absolute symbols (`SHN_ABS`) in the ELF. Despite being typed `STT_FUNC`, they have no section membership, so N64Recomp cannot associate them with `.main` during section scanning. This causes the recompiler to generate anonymous `static_N_XXXXXXXX` functions for code targets that fall within these symbols' address ranges, which then fail to compile due to unhandled instructions (`cache`, `tge`).

**Fix:** For every `SHN_ABS` `STT_FUNC` symbol whose address falls within the `.main` or `.entry` section's address range, patch `st_shndx` to the correct section index.

**How it was discovered:** The recompiler emitted `static_6_800A7060` (failing with `Unhandled instruction: cache`) and `static_6_800A2F60`. Investigation showed `osInvalICache` at `0x800A7060` and `osSetIntMask` at `0x800A2F60` were both `SHN_ABS` — section scanning created anonymous statics at those addresses instead of recognizing the named symbols.

**Scope:** ~200+ libultra/NuSystem symbols patched. All have addresses in the range `0x80025C50`–`0x800D2930` (.main).

### Patch 3: jr v0 at 0x800A384C → nop

**Problem:** `func_800A2F50` has a `jr ra` at offset +4 (address `0x800A2F54`), making the recompiler believe the function is only 0x10 bytes. The actual function body continues to `0x800A3854`. A `jr v0` (jump register) instruction at `0x800A384C` references a jump table at `0x800D2280` whose size the recompiler cannot determine (`Failed to determine size of jump table at 0x800D2280`). This causes `static_6_800A2F60` to be generated incorrectly and fail.

**Fix:** Nop the `jr v0` at `0x800A384C` directly in the binary. The instruction encoding `0x00400008` is replaced with `0x00000000`.

**Why not stub func_800A2F50:** Stubbing prevents recompilation of the function but does not prevent section scanning from discovering the jump table. The static is generated during scanning, before stubbing takes effect.

## Stubs (mariogolf.toml)

29 functions are stubbed out — they are replaced with empty no-op implementations in the recompiler output. Stubs fall into two categories:

### Callers of ADD30 overlay absolute symbols

The `.ADD30` section is a pure data overlay (no `X` executable flag). Its symbols are typed `ABS` and cannot be resolved by the recompiler as callable functions. Any `.main` function that calls into `.ADD30` via `jal` to an absolute address fails with `No function found for jal target`. These callers are stubbed:

```
func_80025D54, func_800469EC, func_800487E4, func_80080688, func_800451E4,
func_80080E14, func_80048D7C, func_80086864, func_80045CE0, mainproc,
func_80044FDC, func_8008679C, func_80080C4C, func_80081D4C, func_8008C6B0,
func_80025D30, func_80089094, func_8008060C, func_80084468, func_8008085C,
func_80080E7C, func_800427E8, func_80046604, func_8008534C, func_8004B474,
func_80045C00, func_8008CD30
```

### Functions with unhandled instructions

```
overlays   — contains tge instruction (unhandled by recompiler)
func_800A2F50 — contains cache instructions; also generates unresolvable
               static due to jump table (see Patch 3 above)
```

**Note on `overlays`:** This is a function literally named `overlays` at `0x800B5F58` in the `.main` section, not the overlay system itself. It contains `tge` (Trap if Greater or Equal), which N64Recomp does not implement.

## Why No relocatable_sections_path

An earlier version of the pipeline used `relocatable_sections_path = "overlays.txt"` pointing to a file containing `..ADD30`. This was removed because `.ADD30` has no executable functions — it is a pure data overlay. Declaring it as relocatable served no purpose and caused `Failed to find written section index of relocatable section: ..ADD30` errors on output.

## glabel .type Fix (mariogolf64 repo)

A prerequisite for this pipeline is that the mariogolf64 repo's `include/labels.inc` emits `.type \label, @function` for every `glabel` definition. Without this, assembly functions are typed `NOTYPE` and N64Recomp cannot determine their boundaries.

This change was made in the mariogolf64 repo (`squash/decomp-overlay-manager-v2` branch) and increases `FUNC`-typed symbols from 265 to 4,458. The ROM MD5 is unaffected.

## Output

A successful run produces in `recomp_output/`:

| File | Contents |
|---|---|
| `funcs_0.c` – `funcs_7.c` | Recompiled C functions (50 per file, 4,677 total) |
| `funcs.h` | Function declarations |
| `recomp_overlays.inl` | Overlay/section table for the runtime |

The output is consumed by [MarioGolf64Recomp](https://github.com/jebsmartt/MarioGolf64Recomp) via the `RECOMP_OUTPUT` CMake variable.

## Known Limitations

- The `tge` instruction is unhandled by N64Recomp. Functions containing it must be stubbed. Mario Golf uses `tge` as a compiler-generated assertion trap — stubbed functions lose this behavior but it is non-critical for port functionality.
- The `cache` instruction is unhandled. Cache management functions (`osInvalICache`, `osWritebackDCache`, etc.) are present in the output as section-bound symbols but their callers that reach them through absolute symbol paths are stubbed. The runtime's ultramodern layer handles cache coherency on the host platform.
- `func_800A2F50` is both stubbed and has a binary patch applied. The stub prevents recompilation; the patch prevents static generation during section scanning. Both are required.
- ADD30 overlay functions (`0x801F4A30`+) are not recompiled. They are called at runtime via `LOOKUP_FUNC` which the MarioGolf64Recomp runtime must implement.
